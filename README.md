# OpsQuery — safe, measured text-to-SQL over operational data

**Status: v1.0.0.** Ask a question about ERP/POS data in plain English; get a correct, cited,
read-only answer — or an explicit refusal.

Most "chat with your data" demos can write to your database, and nobody can tell whether the
answers are right. OpsQuery treats both as the product: a guard plus a read-only role for safety, an
injection-resistant retrieval path, and an eval suite that gates CI the same way tests gate a
release.

Generated by `make report` from [`reports/eval.json`](reports/eval.json); never typed by hand.

| Metric | Baseline | OpsQuery | Status |
|---|---|---|---|
| SQL execution accuracy (golden set) | 0.064 | 1.000 | gate: 1.000 |
| Held-out execution accuracy | - | 1.000 (12/12) | reported |
| Citation groundedness | - | 1.000 | gate: ≥0.95 |
| Retrieval recall@5 | - | 0.950 | gate: ≥0.85 |
| Unsafe-query refusal rate | 0.000 | 1.000 | gate: 1.000 |
| False executions in adversarial set | - | 0 | gate: 0 |
| Cost per query / p95 latency | - | $0.0000 / 132 ms | reported |

63 scored cases (including 12 held out until release), 15 adversarial cases, 20 labelled retrieval
queries. The baseline is a deliberately naive single-prompt planner; it scores 4/63, which is the
point — the traps discriminate instead of inflating.

> **Honesty note.** `make eval` measures the deterministic offline planner that ships as the
> default proposer. It is a rules-based text-to-SQL system, not a live LLM. Every SQL statement is
> still executed against the seeded database and compared to an independently written golden query,
> so the accuracy is a real execution-accuracy measurement of that system. The LLM path
> (`llm/client.py`, cassettes) exists for provider-backed runs and replays offline in tests; it is
> not what produced the 1.000. See the case study for what that does and does not prove.

## Quickstart

```bash
make setup          # uv sync (Python 3.12, ruff, mypy, pytest)
make db-up          # postgres 16 + pgvector on localhost:55432
make seed           # deterministic 256,573-row dataset + 20 policy docs
make ci             # lint → types → tests (89% coverage) → eval gate
make demo           # cited answer, refusal, blocked injection
make eval           # writes reports/eval.json
make report         # markdown table from the report
```

`make ci` is self-sufficient: it starts the database, runs the test suite against an ephemeral
database, then re-seeds and runs the eval gate.

## Architecture

```
src/opsquery/
  sql/guard.py         parse one statement, SELECT-only, table/column allowlist, bounded LIMIT
  db/executor.py       read-only role, 5s timeout, 10k row cap, typed rows, order-insensitive hash
  db/introspect.py     deterministic 81-line catalog (types, FKs, samples, row counts)
  agent/planner.py     deterministic offline SQL planner + naive baseline
  agent/loop.py        ≤6 tool calls: run_sql, retrieve_docs, finish; no write tool exists
  agent/refuse.py      destructive / out-of-scope / injection / raw-PII refusals
  rag/chunk.py         lossless heading-aware chunks with offsets
  rag/index.py         deterministic 256-d embeddings, pgvector + lexical reranking
  rag/cite.py          citation assembly and claim-level groundedness
  rag/injection.py     document-level quarantine of instruction-bearing text
  security/redact.py   email/phone/card/account masking for results and context
  observability/      OpenTelemetry spans per step
  eval/                dataset schema, runner, RAG metrics, report
```

## Safety invariants

- **No write path.** The tool registry contains only `run_sql`, `retrieve_docs`, `finish`.
  `test_no_write_tool_exists` is permanent.
- **Guard before prompt.** Every SQL statement passes `sql/guard.py`; 100% branch coverage is
  enforced by `make test`.
- **The database is the second line of defence.** `ops_readonly` has SELECT only,
  `default_transaction_read_only=on` and `statement_timeout=5s`. Bypassing the guard still cannot
  write.
- **Retrieved text is data, never instructions.** Documents are delimited as
  `<untrusted_document>`; a document containing instruction-like text is quarantined as a whole.
- **Refusal is a feature.** 15/15 adversarial requests refused, 0 false executions.
- **No live LLM in tests.** Cassette replay is network-free and deterministic; recording requires
  `OPSQUERY_RECORD=1` plus credentials.

## Domain

ERP/POS for a small business: customers, products, suppliers, inventory, orders, order items,
invoices, payments, support tickets. The deterministic generator (`seed=42`) includes seasonality,
duplicate customer names, NULLs, negative stock adjustments, refunds as negative payments, and UTC
boundary orders — the awkward rows the eval set probes. See [seed/DGP.md](seed/DGP.md).

## CV block

**OpsQuery — safe, measured text-to-SQL agent** (Python, PostgreSQL/pgvector, sqlglot, OpenTelemetry)

- Built a read-only analytics agent with a parse-based SQL guard, table/column allowlists and a
  database role that rejects writes independently; 100% branch coverage on the guard.
- Measured execution accuracy against 63 golden questions and 12 held-out cases, with a naive
  baseline at 0.064 and 15/15 adversarial refusals, 0 unsafe executions.
- Built offline hybrid retrieval over 20 policy documents (recall@5 0.950) with chunk-level
  citations and document-level quarantine of prompt-injection attempts.
- Added PII redaction, per-step OpenTelemetry tracing and a CI gate that blocks accuracy, safety or
  groundedness regressions.

## Not in scope

- Writing anything to the database. Ever.
- Fine-tuning. Prompt/context engineering and retrieval quality first.
- A production chat UI. The demo is one page plus JSON, deliberately.
